How each day works

A project, then a kata

The tests say when you're done, so you never compare your code with someone else's.

1 The project

  1. Read the brief. Something real: matatu fares, a chama ledger, a booking API.

  2. Write Go in starter/. The function names are there; the body is yours.

  3. Run go test until it says ok. A failing test shows what you returned next to what it wanted.

  4. Then read solution/, commit, and tick the day off here.

2 The kata

  1. A 5–15 minute puzzle in the format HackerRank uses: read stdin, print stdout.

  2. Judge it locally with go run ./tools/kata 1. Wrong answers and slow code both fail.

  3. A hundred of them later, timed tests are routine.

The daily kata

Practise for the test before the test

Same rules as HackerRank: exact output, a time limit, hidden big inputs. The judge runs on your machine, so you can try as often as you like.

More than syntax

What working engineers are expected to know

Most courses stop at the language. This one covers the things you're asked about in your first code review.

Day 21

Env variables and secrets

Config from the environment, .env for local work, and what to do in the first hour after a key leaks.

Days 50–51

HTTP methods and status codes

Which methods are safe and idempotent, PUT versus PATCH, and 401 versus 403.

Days 57–61

OWASP Top 10

Injection, broken access control, password hashing, CORS and security headers, in Go.

Days 27–40

Algorithms

Big-O, two pointers, binary search, graphs and dynamic programming, ending in a timed mock test.

Days 41–48

Concurrency

Goroutines, channels and context, checked with the race detector.

Days 62–63, 81

Tests, CI and observability

Integration tests against a real database, GitHub Actions, logs, metrics and traces.
